# 资源门禁测量环境澄清(owner 授权,2026-10-06)

> 工单:#421(T7 Python 测试族)/ 父 spec:#412 · 结论:AC1/AC2 的 RSS 门以
> **CI 受控环境双平台全绿**为验收基准;spec 的 1700MB 数字本身不变;本地
> 数字作为报告性证据记录,不作门禁。相位交换方案经评估否决,不立工单。
> CI 证据:run 37361188600(macOS 944.6MB / Windows 948.7MB 长音频峰值,
> 双平台 RESOURCE-GATE: PASS)。

## 背景

T7 资源门禁(ticket #421)第二轮评审发现:引擎侧根因修复(7a94a82:DSP
全局 float64 rfft 改分块 overlap-add FIR;VAD 整文件单次喂入改 ≤60s 窗口
独立 pass)已把长音频峰值从确定性 FAIL 3735MB 降到 ~1660-1682MB,但本地
10 核 mac 开发机上 5 次直接采样 2 次超门(1914.1/2083.0MB),并发双任务
3 次采样 2 次超门(2043.9/2049.3MB),失败率 30-40%,门限摆动。

## 实测证据链(全部本机 macOS arm64 10 核,嵌入式 python 3.11)

### 引擎修复有效性(已合入 7a94a82)

| 项                       | 修复前             | 修复后                            |
| ------------------------ | ------------------ | --------------------------------- |
| 长音频峰值(生产协议路径) | 确定性 2829-3936MB | 低模式 1658-1682MB                |
| 双任务并发峰值           | 1728-2041MB        | 低模式 1452-1463MB                |
| ASR 分块循环本身         | —                  | 平坦,+278MB 工作集,多次调用无增长 |

根因为两个全文件瞬态:DSP 高通对整条音频跑一次全局 float64 rfft(~1GB),
VAD 适配器整文件单次喂给 funasr_onnx(~1GB)。修复后均为 O(块)/O(窗口)。

### 残留摆动的定位:加载期分配布局多模态(非泄漏)

- 生产协议路径 spawn 后基线(三模型全部加载成功,status 实测
  `asr/vad/punc` 全 true、`punc_loaded=True`)按进程多模态:
  **1311 / 1317 / 1319 / 1584 / 1890 / 1901 / 1904 MB**(10+ 次采样)。
- 单模型单独加载完全确定:asr 885-891MB(×2)、punc 991MB(×2)、vad ~3MB。
- 只有 initialize() 的**并行加载线程**产生多模态;顺序加载稳定但 ~1.77GB
  (raw ORT 四模型 ×3:1772/1783/1798MB,arena 开关无差别)。
- vmmap --summary(高模式样本):ps RSS 1901MB 中 **1.8GB 为可写常驻**
  (非 mmap 文件页;只读库常驻仅 342.7MB)——是分配布局而非页缓存计入。
- 立即复测即复现(2026-10-06 第三轮):长音频 3/5 超门(2182-2189MB),
  并发 1/3 超门(2040MB),与评审 30-40% 失败率一致。

### ORT 内存杠杆全部无效(punc 会话独占 880-920MB @ 283MB int8 文件)

- `session.use_ort_model_bytes_directly` / `use_ort_model_bytes_for_initializers`
  / `session.disable_prepacking`:单独与组合实测均无差(punc 加载 ~992MB 五臂)。
- `enable_cpu_mem_arena`:funasr-onnx 已默认 False;显式开启对加载/推理
  RSS 无实质差(四模型顺序加载 arena off 1772-1798 vs on 1727-1766)。
- ORT 版本:1.24.1 / 1.27.0 / 1.30.0 punc 加载增量一致(+877-880MB)。
- `malloc_zone_pressure_relief`(libSystem ctypes):使子进程崩溃,不可用。
- ORT 线程数 8/4/2:不消除双模(长音频 1655-2192MB 三组各 3 次)。

### 相位交换评估(否决,不立工单)

punc/ASR 相位交换生命周期无法作为本验收项的修复:

1. **约束不了 AC2 并发峰值**:AC2 要求 mic + file 双任务并发,两任务同时
   合法持有 ASR,mic 在文件任务的 ASR 窗口内也需要 punc 标点——交换窗口
   要么被并发任务复活已释放模型(竞争,峰值回弹),要么在模型锁下串行化
   (死锁风险消除但 ASR 阶段峰值不变,而那正是峰值所在)。
2. **代价**:每次转录 +3-6s(punc 加载 + asr/vad 重载),check_status 出现
   `initialized=false`/`models.punc=false` 瞬变,触及 #177/#189 建立的
   卸载/重载生命周期语义(高风险区)。
3. 收益仅限单流长音频的 punc 阶段,而峰值实际发生在 ASR 阶段。

## 决议(owner 授权,2026-10-06)

1. AC1/AC2 的 RSS 门以 **CI 受控环境双平台全绿**为验收基准(run
   37361188600:长音频 944.6/948.7MB、并发 1170.9/919.4MB、冷启动 p95
   7.53/7.57s,双平台 RESOURCE-GATE: PASS)。理由:spec 用户故事 6 的目标
   环境是 8GB Windows 笔记本,CI runner(少核、受限)比 10 核开发机更接近
   该目标;本地多模态是并行 initialize() 的 ORT 分配布局彩票,vmmap 证实
   有界、非泄漏。
2. **spec 的 1700MB 数字不变**;门禁常量(RSS≤1700/RTF≤0.1/≥600s/冷启动
   p95<看门狗)维持钉死。本地低模式 1658-1682MB(过门)、高模式 2083-2192MB
   作为报告性证据记录,不作门禁。
3. 相位交换否决,不立工单;本评估原文归档供未来参考。
4. 若未来需要在本机类环境收敛该多模态,先拿到的证据是:并行加载布局是
   唯一变量(顺序加载稳定但更肥),应从 initialize() 的加载编排入手做
   专项实验,而非推理栈配置。
